# 项目对比分析专题 · 后端直接执行 SQL（方案 B）实施记录

> 日期：2026-11-12　状态：**已实施**（不创建/不依赖 Superset 数据集；与「成本分析」同一套后端 SQL 专题机制）
> 页面：`/analysis` → 「项目对比分析」卡片 → `/analysis/project-compare`

## 1. 目标与形态

在「专题分析」大厅新增第 6 个专题 **项目对比分析**：

- **数据链路类似成本分析**：专题页的全部查询（项目排名 + 项目对比）都由
  `/api/v1/bi/analysis/chart-data` 执行专题自己的精简 SQL（大陆 + 海外双侧），
  **不建独立数据集、不直接沿用 dataset 26**；`dataset 26` 只保留给其它未完工专题与筛选值候选。
- **功能类似现有「对比模式」**（仪表板图表卡片的「对比」弹窗）：选择多个项目，按
  **上线 / 首测 / 二测 / 三测** 锚点各自对齐「锚点后 N 天」窗口（窗口结束不超过下一阶段起始日期），
  横向对比项目的消耗、付费与回收表现。
- **整页即对比视图**（第二轮调整）：该专题**不再渲染核心指标 / 趋势 / 维度拆解**，对应查询也不再发出；
  正文就是「项目对比」视图（项目、指标 + 趋势图 + 分基准对比表）。
- 筛选条即控制台（第三/四/六轮调整）：**基准、窗口、项目、指标四个控件全部做成顶部筛选条内的
  Autocomplete**（基准多选、窗口单选、项目多选、指标单选），与媒体、渠道商并列并写入 URL；
  **日期范围被「基准 + 窗口」替代**（不再渲染，也不再发对应查询）；「主游戏」「地区」「平台」筛选移除，
  URL/面包屑带入的隐藏参数会被忽略，保证"可见范围 = 实际范围"。
- **不自动设置基准与项目**（第六轮调整）：进入页面时基准与项目均为空，视图提示先选基准、再选项目，
  用户未选择前**不发出任何对比查询**；没有"消耗 Top5/默认上线"之类的隐式选择。
- 页头不显示「刷新」按钮（对比视图自带「重新查询」），也不读写默认视图快照、不被大厅预热。

### 3.1.1 充值流水 / 商户充值 / 流水ROI（与旧数据集对齐）

旧数据集 26 / 38 的这两列口径如下，项目对比专题按同一口径补齐，并放在「新增进入」之后：

| 列 | 大陆（dataset 26） | 海外（dataset 38） |
|---|---|---|
| 充值流水 | 运营表 `p_money`（D0 cohort 当日全量充值），按 `(report_date,cch_id,papp_id)` 取；因广告粒度含媒体/团队，按该键行数 `COUNT(*) OVER(...)` **均摊**到广告行 | `all_app_pay_log` 按支付日 `SUM(paid_usd)`，`paid_status=1`，按 `(report_date,papp_id,ad_cch_id,system,region)` 聚合 |
| 商户充值 | 运营表 `switch_pay_amount`（手游）/ `pos_p_money`（小游戏），同样均摊 | `SUM(paid_tax_usd)` 排除 `payment_id in (19,20)`，×7/10000 |
| 流水ROI | 充值流水 ÷ 返点后消耗（命名比率，合并后重算） | 同左 |

实现说明：

- 大陆窄 SQL / 宽 SQL 都新增 `operate` CTE（手游+小游戏运营表），与广告行 `FULL OUTER JOIN` 后按
  `platform + report_date + cch_id + papp_id` 的 `COUNT(*) OVER` 均摊——只有消耗/充值、没有广告归因的键
  也会保留一行（与旧数据集一致），所以任意媒体子集求和仍等于运营表总额。
- 海外新增 `pay` CTE（`all_app_pay_log`），与广告聚合按 5 键 `FULL OUTER JOIN`；本专题广告粒度在同一键上唯一，
  因此是 1:1 关联，充值流水/商户充值即为支付日到账金额。
- `all_app_pay_log` 是 LIST(corder_year) 分区表，若用 `TO_CHAR(...)` 过滤会扫全部分区；为此新增
  `/*BI_EPOCH_WINDOW:paid_date_s*/` 标记：编译时按窗口日期注入
  `paid_date_s >= extract(epoch from timestamptz '<start> 00:00:00+08') - 86400`（±1 天兜底时区），
  并附带 `corder_year between start_year-1 and end_year+1` 以命中分区；外层 `日期` 条件仍保证精确窗口。
- 新增 `流水ROI` 命名比率到专题 metrics；前端指标目录与列顺序加入
  「充值流水 / 商户充值 / 流水ROI」，位于「新增进入」之后。
- 一致性校验（`analysis_consistency.py`）的 project-compare 指标集同步扩展为 9 个原始列 + 8 个比率，
  窄/宽视图都含运营表列，继续逐值对账。

### 3.1.2 对比表列顺序（业务指定）

对比表 / 图表指标选择器的列顺序（`PROJECT_COMPARE_METRIC_KEYS`）：

```
消耗 → 返点后消耗 → 新增进入 → 自然新增% → 充值流水 → 商户充值
→ CPA → CPP → 1日付费数 → 1日付费率
→ [ROI 组] 流水ROI → ROI1 → ROI2 → ROI3 → ROI4 → ROI5 → ROI6 → ROI7 → 累计ROI
→ [LTV 组] LTV1 → LTV2 → LTV3 → LTV4 → LTV5 → LTV6 → LTV7 → 累计LTV
→ [留存组] 2日留存率 → 3日留存率 → 7日留存率
```

- 指标组按 **ROI → LTV → 留存** 连续排列，组内保持回收阶段顺序；ROI/LTV 均补足 1–7 日，命名统一为 `ROI1`…`ROI7`、`LTV1`…`LTV7`；
- `自然新增%` 紧跟在 `新增进入` 之后；`1日付费数` 放在 `1日付费率` 之前；
- `LTV1…LTV7` 表头统一为 `LTV1`…`LTV7`（`LTV-第N天` 的原始标签只保留在趋势图指标目录里）；
- 所有列（表头、项目行、明细行）统一**居中对齐**；
- 对比表不再展示 `1日充值`、`累计充值`、`累计付费数`（SQL 仍保留这些列，`LTV1`/`累计LTV` 等比率继续使用）；
- 2/3/7 日留存率对最近 2/3/7 天窗口仍未成熟，展示值会偏低（与其他留存类指标同一特性）。

### 3.1.3 明细表格按时间视图维度展开

对比表每个项目行支持展开（行首 chevron 或表头「展开明细/收起明细」），展开后按**当前图表的时间视图**
（日/周/月，与图表右上角切换一致）显示该窗口内的分桶明细：

- 子行 = 一个时间桶：`第N天 / 第N周 / 第N月`，`窗口` 列显示对应自然日期（日：`YYYY-MM-DD`；
  周：`YYYY-MM-DD ~ YYYY-MM-DD`；月：`YYYY-MM`）；
- 子行指标与窗口合计同一聚合口径：加法指标求和，比率指标按分母加权
  （`aggregateBucketMetric` + `bucketWeight`），无数据桶显示「–」但保留序号；
- 切换 日/周/月 不重新请求接口，展开行就地按新粒度重算（复用图表分桶逻辑
  `groupSectionRowsByBucket`，新增纯函数 `projectCompareBucketRows`）；
- 父行保持原有「最优值高亮」，子行不做跨项目比较高亮。

### 3.1.3.1 展开明细时折叠图表

- 展开状态提升到页面级（`ProjectCompare`），各锚点表只做受控展示，因此页面能感知“是否有明细展开”；
- 任一行展开后图表**整体折叠**（`max-height` 过渡到 0、透明度淡出，仅保留卡片标题与控件），
  纵向空间全部让给明细表；全部收起后图表自动恢复；
- 过渡刻意做得轻：`max-height 200ms ease` + `opacity 160ms ease`，无弹跳/回弹，图表节点保持挂载避免重新渲染；
- 图表折叠后对比表**自适应填充剩余视口高度**（`height = innerHeight - 折叠后表格顶部 - 40`）；
  折叠开始时即按「当前图表高度」预测折叠后的位置，**表格扩展与图表折叠同时开始**（无先折叠再填充的等待）；
  窗口 resize 与过渡期间跟随 scroll 重新测量，`height/max-height 160ms ease` 过渡；收起明细后恢复 480px 上限，避免下方留白；
- 明细行抽成 `memo` 组件，避免高度/折叠状态变化重复渲染数百个单元格（长任务从约 3 段降到 1 段）；
- 卡片标题栏右侧提供「展开图表 / 折叠图表」手动切换，明细展开期间也可以临时看图表；
- 项目/基准/窗口变化（查询计划变化）时自动清空展开状态，避免残留旧 key。

### 3.1.4 表格紧凑模式与横向滚动条固定

- 对比表使用紧凑模式（`size="small"` + 单元格 `py: 0.25 / px: 0.75`、`fontSize: 0.75rem`）：
  行高由约 41px 降到约 25px，23 个指标列在宽屏（≥2200px）可一屏放下，窄屏需要横向滚动。
- 表格自身横向滚动条位于 480px 滚动区底部，可能落到视口外，因此在表格下方增加
  **sticky 横向滚动条代理**（`position: sticky; bottom: 0`，`data-testid="project-compare-sticky-scrollbar"`）：
  - 宽度与表格实际 `scrollWidth` 同步，表格滚动 / 代理滚动双向同步 `scrollLeft`；
  - 仅在表格内容宽于容器时显示（窄屏出现，宽屏不占位）；
  - 表格原生横向滚动条隐藏，避免出现两条横向滚动条。
- 展开明细行沿用同一紧凑行高。

### 3.2 命名比率指标（后端定义，`_RATIO_METRIC_RE` 拆分后合并重算）

| 指标 | 定义 |
|---|---|
| `cpa` | 返点后消耗 ÷ 新增进入 |
| `cpp` | 返点后消耗 ÷ 1日付费数 |
| `自然新增%` | 媒体=自然量 的新增 ÷ 全部新增 |
| `ltv_1` / `roi_1` | 1日充值 ÷ 新增进入 / 返点后消耗 |
| `ltv_cum` / `累计roi` | 累计充值 ÷ 新增进入 / 返点后消耗 |
| `流水ROI` | 充值流水 ÷ 返点后消耗 |
| `1日付费率` / `2日留存率` / `3日留存率` / `7日留存率` | 1日付费数 ÷ 新增进入 / 2日留存数 ÷ 新增进入 / 3日留存数 ÷ 新增进入 / 7日留存数 ÷ 新增进入 |
| `ltv_2` … `ltv_7` | 第 N 日充值 ÷ 新增进入（表头显示 `LTV2`…`LTV7`，与 `LTV1` 命名一致） |
| `roi_2` … `roi_7` | 第 N 日充值 ÷ 返点后消耗（表头显示 `ROI2`…`ROI7`，与 `ROI1` 命名一致） |

### 3.3 对比窗口语义（复用仪表板对比模式）

- `start` = 该游戏在所选锚点下的起始日期（渠道 → 全游戏，缺失则该组合跳过并在 UI 提示）；
- `end`（不含）= `start + N 天`，且不超过下一阶段（首测→二测→三测→上线）的起始日期；
- 查询 `time_range = "start : end"`（后端按 `日期 >= start AND 日期 < end` 执行）；
- 表格/查看 SQL 弹窗中的窗口标注展示**最后一个包含日**：`start ~ (end - 1 天)`。
  例如查询 `report_date >= 20260916 and < 20260923` 显示为 `2026-09-16 ~ 2026-09-22`，
  与用户看到的实际数据范围一致（查询参数仍用不含的 `end`）。

### 3.3.1 海外预约消耗（ad_type = 2）归到上线首日

海外事实表 `overseas_report_data.ad_operate_data_report` 的 `ad_type` 区分两类投放：

| ad_type | 含义 | 有无归因新增/充值 | 数据起始 |
|---|---|---|---|
| 1 | 常规买量 | 有 | 2023-01 起 |
| 2 | **预约/品牌类投放（预约消耗）** | **无**（`rt_device_num`、`paid_money` 均为 0） | 2026-07 起 |

预约类投放按实际投放日记在数据里，常常落在上线前几周，会被「锚点后 N 天」窗口裁掉。现在统一处理为：

- 在海外专题基础 SQL 里把 `ad_type = 2` 的行的 `report_date` **替换为该游戏配置的上线首日**
  （`config.profit_sharing."上线时间"`，按 `region=oversea + papp_id` 取最早值）；
- 预约行**不受观察窗日期下推裁剪**（`ad_type = 2 or (原日期窗口条件)`），保证任何包含上线日的窗口都能取到全部预约消耗；
- 没有配置上线时间的项目保持原日期（不迁移）；
- 只影响海外侧（大陆侧没有 `ad_type` 维度）；
- 成本分析（cost）与项目对比（project-compare）共用这一规则，保证两个页面的海外「消耗」口径一致。

上线日期在 Superset 元数据库、不在数据源，因此由后端在编译查询时把
`papp_id -> 上线日` 映射注入 SQL 的 `/*BI_LAUNCH_DATES*/` 标记（只插入整数，无注入风险）：
`compile_query(topic, query, launch_dates)` → `apply_launch_dates()`。
映射也参与响应缓存 key（缓存版本 `v2 → v3`），前端快照版本 `5 → 6`，旧缓存/旧快照自动失效。

### 3.4 口径注意（UI 已注明）

- `累计充值 / 累计付费数是「窗口内新增用户截至当前的累计值」`，随数据回补与上线时长变化；
  跨项目/跨窗口比较回收效率时以 `ROI1 / LTV1`（1 日内成熟）为准。
- 因此页面不提供累计类指标的 KPI 环比（第二轮起 KPI 区块整体移除），累计值只在对比表中展示并注明口径。
- **预约消耗归到上线首日后**，包含上线首日的窗口「消耗」会包含预约成本，而「新增进入 / 充值」不变，
  因此上线首日与窗口的 CPA/ROI 会相应变化（预约成本属于上线获客成本的一部分）。
- 以「首测 / 二测 / 三测」为基准时，预约消耗已被记到上线首日，若该日不在观察窗内则不计入——
  预约成本只属于上线，不摊到测试轮。
- 比率指标在日粒度由后端按当日 SUM(分子)/SUM(分母) 重算；前端做「窗口合计 / 周 / 月」聚合时，
  按各指标声明的 `bucketWeight` 分母做加权（如 CPA 用新增进入、ROI1 用返点后消耗），
  与直接跑整窗查询的结果一致（E2E 有逐值校验）。

## 7. 已知限制与风险

1. **累计口径**：`累计充值 / 累计付费数` 为窗口内新增用户截至当前的累计值，受上线时长与数据回补影响；
   不做跨窗口的「N 日回收」对齐（若要做，需要再暴露 `rt_paid_money_N` 并按窗口 N 动态选列，属后续迭代）。
2. **性能**：项目对比查询数 = 选中项目数 × 选中基准数，全部合并进一次批量请求（后端最多 4 线程并发 +
   Redis 缓存）；默认 5×1=5 条无压力，手动多选较多项目/基准时耗时线性增长，暂未设硬上限。
3. **页面级筛选与侧别过滤并列**：对比查询按项目侧别追加 `地区=mainland` / `平台=oversea` 消歧；
   若用户手工选择了与该侧别冲突的地区/平台页面筛选，结果为 0 行（显示 –），不报错。
4. **项目起始日期来源**：`/project/profit-sharing` 中无 `region` 的历史行会按 domestic 归一后匹配，
   若线上存在完全无 region 的旧数据，相关项目可能不出现在可选列表。
5. 「对比表最优值高亮」只在当前窗口内比较，跨项目不同窗口长度（被下一阶段截断时）仅作参考。
6. **不提供默认选择**：进入页面时基准与项目为空（无消耗排名、无默认上线时间），
   用户需要先在筛选条选择；「重置」清空回初始状态。
7. **图表粒度切换是纯前端分桶**：日/周/月只重新聚合已取回的日行，不重新查询；月桶按自然月与
   窗口起始月差编号，月中起窗时「第 1 月」为不完整月（图表 Tooltip 已说明）。
8. 页头「刷新」对该专题隐藏（对比视图自带「重新查询」），页头不再承载无效操作；
   同时该专题不读写默认视图快照、不参与大厅预热。
9. 基准/窗口属于页面筛选状态（写入 URL），因此刷新页面、复制链接、在大厅与专题间跳转都能保留；
   它们只对「项目对比分析」专题生效，其它专题即使 URL 携带也会被忽略、且非默认值才写入链接。
