## 1.1 执行 SQL 的数据来源

历史宽视图 `report_sygame_ad_data_view`（405 列）/ `report_minigame_ad_data_view`（407 列）本质上就是
「消耗分支 UNION 归因充值分支」，并给缺失列补 0。执行版 SQL 直接读这两个分支（源团队维护的窄视图）：

| 侧 | 执行 SQL 引用（窄） | 历史宽视图（对照，不参与执行） |
|---|---|---|
| 大陆·手游 | `sj_report_data.ad_deplete_view`（消耗，38 列）+ `sj_report_data.ad_data_sum_report`（充值/归因） | `sj_report_data.report_sygame_ad_data_view` |
| 大陆·小游戏 | `sj_report_data.wxh5_ad_deplete_view` + `sj_report_data.wxh5_data_sum_report` | `sj_report_data.report_minigame_ad_data_view` |
| 海外 | `overseas_report_data.ad_operate_data_report` | 同左（历史 dataset 38 也是它） |
| 维度 | `ad_manager.ad_channel`、`sj_platform.part_channel`、`sj_platform.part_papp`、`xh_osdata_manage.ad_channel`、`xh_osdata_manage.part_papp` | 同左 |

**数据一致性保证**（详见 `宽窄一致性校验.md` 与 `宽窄一致性校验报告.json`）：

- 逐值等价是结构性的：宽视图就是这两条分支的 UNION ALL，且宽视图对缺失列补 0；
  执行 SQL 按同样的键聚合两分支，SUM 结果必然一致。
- 实测校验：同一分析查询分别用「窄视图 SQL」与「历史宽视图 SQL」编译，**在同一 REPEATABLE READ 事务快照内**
  读取大陆库逐行逐列比对。覆盖 **6 个时间窗 × 8 种查询形态 = 48 项检查 / 5587 行**：
  **48/48 通过，最大绝对/相对差异均为 0**。
- 可复跑（退出码 0=一致，1=有差异，可挂定时对账）：
  ```bash
  docker exec superset-superset-light-1 python -m superset.project.bi.analysis_consistency
  ```

## 7. 修复记录：维度拆解表日期显示异常（2026-11-10）

**现象**：成本分析「维度拆解表」切换到「日期」维度时，日期列显示为 `1791676800000` 这样的数字，而不是 `2026-10-11`。

**根因**：方案 B 接口在序列化结果时用了 pandas `to_json`，DATE 列被转成 **epoch 毫秒**；
前端表格先把值 `String()` 化再交给 `formatFullDay`，数字字符串无法被 dayjs 解析，于是原样显示数字。
历史 dataset 链路用 Superset 的 `df_to_records` 序列化，DATE 是 ISO 字符串（`2026-10-11T00:00:00`），所以旧页面正常。

**修复**：
1. 后端 `superset/project/bi/api.py` 新增 `_analysis_records()`：使用 Superset 的 `df_to_records` 序列化，
   并把 TEMPORAL 列规范化为 `Timestamp`（输出 `2026-10-11T00:00:00`，与历史链路一致）；
2. 分析结果缓存 key 版本 `v1 → v2`，避免继续返回旧的 epoch 毫秒缓存；
3. 前端快照版本 `4 → 5`，旧快照自动失效；
4. 前端 `formatFullDay` 增加兜底：数字 / 纯数字字符串按 epoch 毫秒解析（兼容旧缓存/旧快照）。
5. 新增回归测试：后端 `_analysis_records` 日期序列化用例、前端 `formatFullDay` 用例。

**验证**：
- light 环境：按日期明细返回 `2026-10-11T00:00:00`，与历史 dataset 26 的 29 行逐值 **0 差异**；
- 生产镜像已重新构建并部署（新镜像 `2026-11-10T01:53:14Z`，回滚标签 `superset-prod-*:rollback-20261110-0950`）；
- 生产验证：按日期明细 29 行、日期 ISO 字符串、与历史 dataset 逐值 0 差异；KPI/下钻/SQL 预览正常；
  `superset_app` 日志无 error。

## 8. 修复记录：下级维度构成 500（Grouper for '日期' not 1-dimensional，2026-11-10）

**现象**：在「按日期查看」的视图里点击趋势图上的异常点，弹出「下级维度构成」时提示
`请求失败：Request failed with status code 500`。

**根因**：该视图的当前拆解维度已经是 `日期`，异常归因查询仍然拼接
`groupby = [当前维度, 日期]`，于是变成 `["日期","日期"]`。后端把两列都命名成 `日期`，
pandas `groupby` 遇到重复列名直接抛 `ValueError: Grouper for '日期' not 1-dimensional` → 500。

**修复**：
1. 前端 `query.ts`：新增 `drillGroupby()`，当前维度就是 `日期` 时只按 `日期` 分组；
   `buildDrillQueryPlan` / `buildDrillAnomalyQuery` 共用（覆盖异常弹窗、预取、日期下钻）。
2. 后端 `analysis_topics.compile_query`：对 `groupby` 做保序去重（防御性，任意重复维度不再 500）。
3. 回归测试：前端「日期维度下钻不重复日期轴」；后端「重复 groupby 编译去重」。

**验证**：
- light 环境：原会 500 的载荷（`["日期","日期"]`）现在 200，返回 30 行；
- 生产已重新构建部署（镜像 `2026-11-10T02:15:26Z`，回滚标签 `superset-prod-*:rollback-20261110-1013`）；

## 13. 修复：为什么"默认日期维度"上线后仍显示主游戏（2026-11-10）

**现象**：第 12 节改为默认「日期」并部署后，仍有用户打开成本分析时表格默认是「主游戏」。

**根因**：页面会把当前视图状态写进 URL（`?range=30d&dim=主游戏...`），
而初始化时 URL 参数优先于专题默认值。用户浏览器里的旧链接带着 `dim=主游戏`，
刷新后 URL 仍把维度恢复成主游戏，新品默认值被它覆盖（部署本身没有问题：
线上 bundle 里成本专题已是 `defaultDimension:"日期"`）。

**修复**：给分析页筛选 URL 增加 schema 版本 `v=2`：
- `filtersToSearchParams` 写入 `v=2`；
- `filtersFromSearchParams` 对**没有 v=2 的旧链接**忽略视图状态参数（`dim`/`date`/`week`/`drill_*`），
  回落到新的专题默认值（日期）；旧链接里的时间范围与普通筛选列仍然保留；
- 新页面写出的链接带 `v=2`，之后显式选择的维度/下钻会正常持久化、可分享。
